# o2a-proxy 价格架构完善方案

> 目标：在保持现有“零迁移兼容”的前提下，补齐 **价格历史/变更处理、费用可信度、套餐与额度、第三方计价适配**，并给出一套可在 Python 引擎与 Rust 桌面端一致落地的分层架构。
> 本文以方案为主，不展开实现代码。

---

## 1. 现状探索结论

### 1.1 当前 o2a-proxy 项目

- **定价数据**：`pricing.json` 为 v1 形态（`<provider>.models.<model>.tiers[]`），支持 `accounts` 账号级覆盖；货币为 CNY，单位是“每百万 Token”。
- **内部模块**：`o2a/pricing/` 已具备
  - `schema.py`：v1 → 内部 v2 归一化；
  - `resolve.py`：服务级 > 账号级 > 模型级的覆盖链；
  - `evaluate.py` + `modifiers/`：discount / batch / schedule / context_tier / free_quota / cumulative_tier 管道；
  - Python 与 Rust（`desktop/src-tauri/src/pricing.rs`）双实现，由 `pricing/golden/cases.json` 保证同构。
- **统计口径**：
  - Python 写入端在记录时把 `cost` 写入 JSONL，并把累计 cost 写入 summary；
  - Rust 读取端用**当前 `pricing.json` + 记录自身 timestamp** 重算历史费用，用于 free_quota 的“当月早于本记录”累计也已实现。
- **额度现状**：
  - 已有 `/quota` 端点、`o2a/quota/` 注册表；
  - 已实现 `local` / `local-rolling-5h` / `manual` / `openrouter`；
  - `services[].pricing` 支持 `""`、`"none"` 和对象 `{"mode": "token"|"subscription"|"free", ...}`；
  - 但目前 `subscription` 主要表现是“隐藏费用”，`pricing_extra`（plan、quota_source 等附加字段）尚未真正接线。

### 1.2 dsh-usage-stats 项目（Ychris12138/dsh-usage-stats）

- **价格计算**（`lib/pricing.js`）：
  - 使用**不可变历史规则目录**：每条规则含 `effectiveFrom` / `effectiveTo`、`currency`、`schedule`（时区 + 峰谷窗口）、`source`、`updatedAt`；
  - 按**事件时间**匹配规则，而不是“当前价格 × 历史 token”；
  - 同一模型同一币种的生效区间不允许重叠（校验失败即抛错）。
- **费用可信度**（`lib/billing.js`）：
  - 累加器记录 `pricedSamples` / `incompleteSamples` / `currencies` / `ruleIds`；
  - 只要存在不可计价样本或混合币种，整体 `costComplete=false`，UI 显示 `—`，不做部分费用；
  - 通过 `pricingFingerprint` 在价格目录或 provider 身份变化时失效缓存，避免用旧缓存展示新价格。
- **套餐/额度**（`lib/subscriptions.js`、`lib/balance.js`）：
  - 提供 OpenCode Go、Z.ai/GLM Coding Plan、Kimi For Coding、MiniMax、Ollama 等订阅额度适配器；
  - 统一归一化为 `windows: [{kind, usedPercent, remainingPercent, resetsAt}]`，并保留 plan 名、状态、降级与 stale 标记。
- **结论**：dsh-usage-stats 的“价格是派生值、按事件时间计价、未知/mixed 失败关闭、额度归一化适配器”思路，正是 o2a-proxy 最值得借鉴的部分。

### 1.3 非 dsh 第三方参考

| 项目 | 参考点 |
|---|---|
| LiteLLM / tokencost / pydantic genai-prices | 统一价格目录（per-million 单价），费用是“token × 单价”的纯计算；价格表通常以版本化 JSON/包更新，缺少强历史计价 |
| one-api / new-api | 用“模型倍率 + token 配额”做二次分发计量，支持用户组、套餐、充值/兑换码；价格调整通过改模型倍率，历史费用一般不做回算 |
| Lago | 计量事件与定价分离；**plan 版本化**、订阅内 allowance/最低承诺/overage、预付费 credit、多币种、幂等事件摄入 |
| OpenMeter | 产品目录中的**versioned plans**、feature/entitlement、usage limit 平衡、按用量计费 |
| TokenToll | YAML 定义 plan（tiered/volume/flat/prepaid/free_tier）、meter、provider pricing；**配置热加载 + replay 重算**，支持硬/软额度 |
| dsh-usage-stats | **事件时间价格规则 + fingerprint 缓存失效 + fail-closed costComplete** |

这些参考共同指向：

1. 用量事件（tokens）是唯一事实；
2. 价格是**目录/规则**，可演进、可版本化；
3. 历史账单应使用**事件发生时的价格规则**；
4. 套餐/额度与按量计价是**两个正交能力**，需要统一抽象。

## 2. 差距判断

当前 o2a-proxy 的价格体系已经具备很好的“解析 + modifier 管道 + 双端镜像”，但要支撑“价格变更、套餐额度、第三方计价”仍缺少：

| # | 差距 | 影响 |
|---|---|---|
| G1 | **无历史价格规则**：`pricing.json` 只保留当前价；改价后历史 JSONL 按新价重算 | 历史月报/账单失真 |
| G2 | **费用“未命中即 0”**：无定价模型、无价格组件或未知币种时直接返回 0 | 用户误以为免费/未计费 |
| G3 | **无币种/来源/规则 ID**：只看到一个数字，无法审计费用依据 | 费用可信度不足 |
| G4 | **服务级覆盖未接入引擎统计**：`resolve_cost` 未传 `service_id`，`pricing.json.services` 形同虚设 | 同一账号不同服务无法按服务定价 |
| G5 | **套餐/订阅模型过于简单**：`pricing.mode=subscription` 只隐藏费用；无 included/overage/free tier/entitlement | 无法表达 GLM Coding Plan、OpenCode Go 等套餐 |
| G6 | **第三方额度适配器覆盖面窄**：仅有 openrouter/manual/local | 缺少 Z.ai、OpenCode Go、Kimi、MiniMax、Ollama、New API、Sub2API/Passion 等 |
| G7 | **价格文件更新缺乏热加载/校验/缓存失效**：引擎侧 `CacheStats._pricing` 长缓存；改了 pricing.json 不一定立即生效 | 改价体验差、双端口径不一致 |
| G8 | **batch 等已注册 modifier 未真正接线**：`meta.batch` 没有从请求/配置注入 | 批量价无法应用 |

## 3. 目标架构（分层）

```
┌────────────────────────────────────────────────────────────────────┐
│  UI / API 层                                                       │
│  /stats  /quota  /pricing-meta  /pricing-reload  桌面面板           │
│  显示 costComplete / 币种 / provenance / 计划额度 / 规则来源          │
├────────────────────────────────────────────────────────────────────┤
│  统计/读取层（Python stats + Rust stats）                            │
│  读取 raw JSONL → 按事件时间 + pricing catalog 派生费用                │
│  fingerprint 失效缓存；free_quota / cumulative 共享同一个“周期累计”    │
├────────────────────────────────────────────────────────────────────┤
│  规则/评估层（o2a/pricing）                                          │
│  RuleCatalog(版本化) → Resolver(service/account/model/事件时间)       │
│  Evaluator(modifier 管道) → CostResult(total/currency/complete/…)    │
├────────────────────────────────────────────────────────────────────┤
│  套餐/额度层（o2a/quota + plans）                                    │
│  PlanRegistry(included/overage/free_tier/windows)                   │
│  QuotaAdapter(openrouter/zai/opencode-go/kimi/minimax/…/declarative)│
├────────────────────────────────────────────────────────────────────┤
│  数据层（不可变事实）                                                │
│  JSONL usage：tokens/timestamp/model/account/service_id/plan_mode    │
│  pricing rules / plans：JSON/YAML 目录，版本化，可热加载              │
└────────────────────────────────────────────────────────────────────┘
```

核心原则：

- **用量记录只写 tokens，不把“费用”当作唯一事实**；费用在读取端按价格目录派生。
- **价格规则按生效区间选择**；当前价只是“没有 `effective_to` 的最新规则”。
- **费用完整性与币种一起返回**；不能确定就 fail-closed。
- **套餐/额度是账号能力，不是模型单价**；两者通过 `service.pricing.plan` 与 `account.quota_source` 关联。

## 4. 关键设计

### 4.1 版本化价格规则（历史计价）

在保留 `pricing.json` v1/v2 兼容输入的同时，引入规则数组：

```json
{
  "version": 3,
  "currency": "CNY",
  "rules": [
    {
      "id": "deepseek-v4-flash-2026-08-16",
      "model": "deepseek-v4-flash",
      "scope": { "service": "*", "account": "*" },
      "effective_from": "2026-08-16T00:00:00+08:00",
      "effective_to": null,
      "components": {
        "input": 1, "output": 2,
        "cache_read": 0.02, "cache_write": 1
      },
      "modifiers": [],
      "source": "https://api-docs.deepseek.com/zh-cn/quick_start/pricing",
      "updated_at": "2026-08-17T00:00:00Z"
    }
  ]
}
```

要点：

- 同 `(service, account, model, currency)` 的规则区间不可重叠，`validatePricingRules` 负责校验（参考 dsh-usage-stats）。
- `effective_from` 为空 = 无上限旧规则；`effective_to` 为空 = 当前仍生效。
- 解析顺序不变：服务级 > 账号级 > 模型级；同一层内用事件时间命中最匹配规则。
- v1/v2 的 `tiers` 仍可自动转成“当前规则”，实现零迁移。

### 4.2 CostResult 增加完整性

```json
{
  "total": 0.123,
  "currency": "CNY",
  "complete": true,
  "breakdown": { "input": 0.1, "output": 0.02, "cache_read": 0.003, "cache_write": 0 },
  "applied": ["free_quota:month"],
  "rule_id": "deepseek-v4-flash-2026-08-16",
  "source": "https://api-docs.deepseek.com/zh-cn/quick_start/pricing",
  "updated_at": "2026-08-17T00:00:00Z"
}
```

行为变化：

- 无规则、未知模型、正 token 但某组件无价格、混合币种 → `complete=false`，UI 显示 `—`。
- 可通过配置开关保留旧“0 元”行为（用于过渡期），但新面板默认展示可信度。

### 4.3 价格目录指纹与缓存失效

- 计算 `pricingFingerprint = hash(规则目录 + provider/route 身份 + 相对配置)`。
- Python `/stats` 与 Rust 统计读取时，若 fingerprint 变化：
  - 丢弃 summary/聚合缓存；
  - 历史数据从 JSONL 重新派生；
  - 不修改 JSONL 中已有的 `cost` 字段（保留为“写入时快照”，展示时以重算为准）。
- 参考 dsh-usage-stats / OpenMeter：缓存不是计费源，只是加速。

### 4.4 服务级定价接线

- `CacheStats._calc_cost` 与 Rust `recalc_cost` 都需要把 `service_id` 传入 `resolve_cost`。
- 这样 `pricing.json.services.<svc-id>.models.<model>` 才能真正生效。
- 账号键序保持 id → name；服务级 > 账号级 > 模型级。

### 4.5 套餐 / 计划目录

在 `pricing.json`（或独立 `plans.json`）新增 `plans`：

```json
{
  "plans": {
    "glm-coding-plan": {
      "mode": "subscription",
      "currency": "CNY",
      "windows": [
        { "kind": "session", "period": "rolling-5h", "unit": "requests" },
        { "kind": "weekly", "period": "week", "unit": "tokens" }
      ],
      "included": { "requests": 500, "tokens": 10000000 },
      "overage": {
        "default": { "unit": "tokens", "input": 8, "output": 24 }
      },
      "free_tier": { "tokens": 100000 }
    }
  }
}
```

- `services[].pricing` 对象增加 `plan` 引用：`{"mode": "subscription", "plan": "glm-coding-plan"}`。
- `pricing_extra` 开始真正参与解析：`PlanRegistry` 把套餐内额度、免费额度、超额价传给 Evaluator / QuotaAdapter。
- 已有 `free_quota` modifier 可以升级为 `plan.free_tier` / `plan.included` 的通用实现。

### 4.6 额度适配器扩展

沿用现有 `QuotaAdapter` 协议，新增：

- `opencode-go`：Bearer usage endpoint / dashboard fallback；
- `zai` / `glm-coding-plan`：quota + subscription 接口；
- `kimi`、`minimax`、`ollama`：Token Plan 剩余窗口；
- `new-api`、`sub2api`、`passion`、`declarative`：余额/额度模板；
- OpenRouter 已有，但可补 credits（Management Key）接口与 `/api/v1/key` 语义区分。

统一快照形状保持现状：`windows[{kind, unit, used, limit, pct, reset_at}] + plan + stale`，前端 `QuotaCard` 无需大改。

### 4.7 热加载与校验

- 为 `pricing.json` / `plans.json` 增加 JSON Schema 校验；启动时加载失败给出明确错误，而不是静默 0。
- 文件变化后支持 `POST /pricing/reload`（或桌面端“重新加载价格”按钮）触发：
  - 重新解析目录 → 计算新 fingerprint → 清除缓存 → 下次读取自动重算。
- 参考 TokenToll 的 hot reload + replay 语义。

### 4.8 其他接线

- `batch`：从引擎请求上下文（batch API / 配置标记）注入 `meta.batch=true`，让 batch modifier 真正生效。
- `context_tier` / `cumulative_tier` / `free_quota`：继续用共享的“周期累计”服务计算，Python 与 Rust 统一口径。
- 多币种：目录内每规则显式 `currency`；不做自动 FX，混合币种 fail-closed。

## 6. 兼容性与风险

- **行为变化风险**：`0 元` → `—` 是老用户可见变化；建议先保留配置开关，逐步默认开启。
- **历史规则维护成本**：不需要一次补齐全部历史；未配置历史规则的时段可用“当前规则”兜底并标记 `complete=false` 或 `approximate=true`。
- **双端一致性**：继续以 `pricing/golden/cases.json` 为共享夹具；新增历史规则与 fingerprint 用例同样双端固化。
- **数据量**：JSONL 仍只写 tokens，费用派生在读取端，不会因为版本化价格而膨胀写入数据。

## 8. 子代理审查结论（o2a glm5.3-flash）

已用子代理按“当前 o2a glm5.3-flash”对方案进行独立审查。审查认为：**方向正确，但需调整 P0/P1/P4 排序与语义闭环**。

### 8.1 审查确认的核心问题

1. 历史规则与 `free_quota/cumulative_tier` 是最大未决风险：必须先规定累计口径（token 还是金额、排序键、能否由 JSONL 重放），否则历史重算会产生递归依赖。
2. fingerprint 失效不能破坏 free_quota 状态；所有额度冲抵状态必须是原始 JSONL 的确定性纯函数，缓存只是加速。
3. scope 优先级用“服务级 > 账号级 > 模型级”不够严谨，应改为**最具体 scope 优先**（如 service+account+model 精确 > 单维 > 通配），并纳入 golden。
4. `0 元 → —` 是可见行为变化，不应在 P0 直接切 UI；需先有历史规则与近似/unknown 分级后灰度。
5. v3 规则 schema、共享 Rust/Python 类型、golden 扩展应提前到 P1，不能留到 P4。
6. 套餐需独立 `plans.json` 并版本化，否则 plan 变更会破坏历史额度展示。
7. 第三方计价不只“额度适配器”，还应考虑 OpenRouter/New API 真实 cost 回填与本地目录价格对账。
8. 建议“只写 tokens / 保留 cost 快照”二选一；若保留快照应改名 `cost_snapshot`，避免双事实。

### 8.2 调整后的推进建议

- 将原 P0 改为“**地基修正**”：不切 UI 默认行为，先钉死累计口径并扩展 golden。
- 将 “v3 JSON Schema + 双端共享类型/golden” 前移到 **P1 与历史价格同批落地**。
- P3 缩为 **declarative + OpenRouter credits + GLM Coding Plan** 三个验证性适配器，验证后再批量扩展。
- P4 只保留热加载、审计 UI、批量补全等收尾工程。
